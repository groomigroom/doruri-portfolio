코드를 보면 **가장 먼저 의심되는 부분은 JavaScript의 `is_liked` 판정과 실제 DB 상태가 서로 동기화되지 않는 것**입니다. 다만 SQL에 아예 INSERT/DELETE가 안 되는 경우에는 몇 군데를 순서대로 확인해야 합니다.

 특히 현재 코드에서는 **버튼을 처음 누르면 POST, 두 번째 누르면 DELETE**가 되어야 하는데, 페이지를 새로고침하면 버튼의 `active` 상태가 DB에서 다시 읽혀오지 않습니다.

 그리고 한 가지 더 중요한 문제가 있습니다. `@DeleteMapping`에서 JSON body를 받는 방식 자체는 가능하지만, Spring Security/CSRF 설정에 따라 DELETE 요청이 차단될 수 있습니다.

 아래 순서로 확인해보세요.

 ## 1\. 먼저 Controller가 실제로 호출되는지 확인

 현재 Controller에 이미 로그가 있으므로:

```
System.out.println("글 ID " + request.getOriginalLink());
System.out.println("사용자 ID " + userId);
```

 버튼을 눌렀을 때 콘솔에 이게 출력되는지 보세요.

 ### 아무것도 출력되지 않는다면

 문제는 Service나 Repository가 아니라 **JavaScript → Controller 요청 단계**입니다.

 브라우저 개발자도구의 `Network`에서:

```
POST /like-link/toggle-like
```

 또는

```
DELETE /like-link/toggle-like
```

 요청이 실제로 발생하는지 확인하세요.

---

 ## 2\. 현재 JS의 가장 큰 문제

 현재 코드:

```
const is_liked = like_btn.classList.contains("active");

const url = "/like-link/toggle-like";
const method = is_liked ? "DELETE" : "POST";
```

 그리고 성공하면:

```
if (is_liked) {
    like_btn.classList.remove("active");
    like_btn.textContent = "취소됨";
} else {
    like_btn.classList.add("active");
    like_btn.textContent = "좋아요함";
}
```

 이 방식은 **DB의 상태가 아니라 버튼의 CSS 클래스만 보고 좋아요 여부를 판단**합니다.

 즉 처음 페이지를 열었을 때:

```
<button class="like_btn">
```

 이므로 무조건:

```
is_liked === false
```

 입니다.

 따라서 무조건 POST가 나갑니다.

 그런데 DB에 이미 좋아요가 있어도 버튼에는 `active`가 없으므로 또 POST가 갑니다.

 다행히 Service에서:

```
boolean exists = likeLinkRepository
        .existsByOriginalLinkAndLikeUserid_Userid(
                originalLink,
                user.getUserid()
        );
```

 중복을 막고 있기 때문에 INSERT가 발생하지 않습니다.

 즉 **페이지 로딩 시 DB의 좋아요 상태를 버튼에 반영해야 합니다.**

 # 3\. 가장 먼저 `LikeLinkEntity`와 Repository를 확인해야 합니다

 지금 올려주신 코드에서 Repository 구현이 빠져 있습니다.

 아마 이런 식일 겁니다.

```
public interface LikeLinkRepository extends JpaRepository<LikeLinkEntity, Long> {

    boolean existsByOriginalLinkAndLikeUserid_Userid(
            String originalLink,
            String userid
    );

    void deleteByOriginalLinkAndLikeUserid_Userid(
            String originalLink,
            String userid
    );
}
```

 이 메서드가 실제 Entity 필드명과 정확하게 일치해야 합니다.

 예를 들어 Entity가:

```
@Entity
public class LikeLinkEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String originalLink;

    @ManyToOne
    private LoginUsers likeUserid;
}
```

 라면

```
existsByOriginalLinkAndLikeUserid_Userid()
```

 는 정상적인 형태입니다.

 하지만 Entity가 실제로:

```
private LoginUsers likeUser;
```

 라면 Repository도:

```
existsByOriginalLinkAndLikeUser_Userid()
```

 가 되어야 합니다.

 **Entity의 실제 필드명을 확인해야 합니다.**

 # 4\. `deleteLike()`에는 트랜잭션이 있으므로 방향은 맞습니다

 현재:

```
@Transactional
public void deleteLike(String originalLink, String userId) {
    LoginUsers user2 = this.loginUserService.getLoginUser(userId);

    likeLinkRepository
            .deleteByOriginalLinkAndLikeUserid_Userid(
                    originalLink,
                    user2.getUserid()
            );
}
```

 이 부분 자체는 괜찮습니다.

 다만 확실하게 하려면 Repository의 delete 메서드를 다음처럼 작성하는 걸 추천합니다.

```
@Transactional
void deleteByOriginalLinkAndLikeUserid_Userid(
        String originalLink,
        String userid
);
```

 Repository:

```
public interface LikeLinkRepository extends JpaRepository<LikeLinkEntity, Long> {

    boolean existsByOriginalLinkAndLikeUserid_Userid(
            String originalLink,
            String userid
    );

    @Transactional
    void deleteByOriginalLinkAndLikeUserid_Userid(
            String originalLink,
            String userid
    );
}
```

 Service에 이미 `@Transactional`이 있으므로 Repository의 `@Transactional`은 사실 없어도 됩니다.

 # 5\. 그런데 현재 `originalLink` 값도 확인해야 합니다

 HTML:

```
<button
    type="button"
    class="like_btn"
    th:data-original-link="${songMainEntity.htmlTitle}">
    삭제하기
</button>
```

 여기서:

```
const originalLink = like_btn.dataset.originalLink;
```

 를 가져옵니다.

 즉 실제로 Controller에 전달되는 값은:

```
songMainEntity.htmlTitle
```

 입니다.

 예를 들어:

```
NewJeans - Supernatural
```

 이런 값일 수 있습니다.

 그런데 DB의 기존 데이터가:

```
/TriplesBabyFlowerCityRemixesAlbum
```

 처럼 **URL을 저장하고 있다면 서로 다른 값**입니다.

 그러면:

```
existsByOriginalLinkAndLikeUserid_Userid(...)
```

 가 항상 `false`가 되고,

```
deleteByOriginalLinkAndLikeUserid_Userid(...)
```

 도 삭제할 데이터가 없게 됩니다.

 따라서 콘솔에서:

```
System.out.println("글 ID " + request.getOriginalLink());
```

 의 값을 확인하고 DB의 `original_link` 값과 **완전히 동일한지** 확인하세요.

 # 6\. `LikeLinkService`에 로그를 추가하면 바로 원인을 찾을 수 있습니다

 일단 다음처럼 바꿔보세요.

```
public void addLike(String originalLink, String userId) {

    System.out.println("===== addLike 시작 =====");
    System.out.println("originalLink = " + originalLink);
    System.out.println("userId = " + userId);

    LoginUsers user = loginUserService.getLoginUser(userId);

    System.out.println("DB userId = " + user.getUserid());

    boolean exists = likeLinkRepository
            .existsByOriginalLinkAndLikeUserid_Userid(
                    originalLink,
                    user.getUserid()
            );

    System.out.println("이미 존재? = " + exists);

    if (!exists) {
        LikeLinkEntity like = new LikeLinkEntity();

        like.setOriginalLink(originalLink);
        like.setLikeUserid(user);

        likeLinkRepository.save(like);

        System.out.println("===== 좋아요 INSERT 완료 =====");
    }
}
```

 삭제도:

```
@Transactional
public void deleteLike(String originalLink, String userId) {

    System.out.println("===== deleteLike 시작 =====");
    System.out.println("originalLink = " + originalLink);
    System.out.println("userId = " + userId);

    LoginUsers user = loginUserService.getLoginUser(userId);

    System.out.println("DB userId = " + user.getUserid());

    likeLinkRepository.deleteByOriginalLinkAndLikeUserid_Userid(
            originalLink,
            user.getUserid()
    );

    System.out.println("===== 좋아요 DELETE 완료 =====");
}
```

 이렇게 해놓고 버튼을 눌러보세요.

 # 7\. 그리고 Hibernate SQL 로그를 켜세요

 `application.properties`에:

```
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
```

 추가하세요.

 더 확실하게 보려면:

```
logging.level.org.hibernate.SQL=DEBUG
logging.level.org.hibernate.orm.jdbc.bind=TRACE
```

 그러면 POST 했을 때 대략:

```
insert into like_link ...
```

 가 나와야 합니다.

 DELETE 할 때는:

```
delete from like_link
where ...
```

 같은 SQL이 나와야 합니다.

 ### 경우를 나누면

 **Controller 로그도 안 나옴**

 → JavaScript / URL / Security 문제

 **Controller 로그는 나오는데 Service 로그가 안 나옴**

 → 거의 가능성이 낮지만 Controller에서 Service 호출 문제

 **Service 로그는 나오는데 INSERT SQL이 안 나옴**

 → `exists == true`인지 확인

 **INSERT SQL은 나오는데 DB에 데이터가 없음**

 → 트랜잭션/DB 연결/롤백 문제

 **DELETE SQL은 나오는데 삭제되는 행이 0개**

 → `originalLink` 또는 `userid`가 DB 데이터와 다름

 이렇게 좁혀갈 수 있습니다.

 # 8\. 또 하나: `likeLinkCount`는 현재 코드와 별개의 문제입니다

 HTML에서:

```
<h2 class="song_main_h2" th:text="${likeLinkCount} + '개'">
```

 를 사용하고 있는데, 좋아요를 AJAX로 추가/삭제해도 이 값은 **서버에서 렌더링된 기존 값 그대로**입니다.

 AJAX 요청이 성공했다고 해서 Thymeleaf가 다시 실행되는 게 아닙니다.

 즉:

```
페이지 로딩
    ↓
Thymeleaf
    ↓
likeLinkCount = 3
    ↓
HTML 생성
    ↓
브라우저
    ↓
POST AJAX
    ↓
DB = 4
```

 가 되어도 화면에는 여전히:

```
3개
```

 가 표시됩니다.

 AJAX 성공 후 숫자를 직접 변경하거나 서버에서 현재 count를 JSON으로 내려줘야 합니다.

 # 9\. 추천하는 구조

 저라면 아예 `toggle-like`라는 이름을 유지하기보다는 현재 구조대로 POST/DELETE를 분리해서 명확하게 만들겠습니다.

 ### Controller

```
@PostMapping("/toggle-like")
public ResponseEntity<?> addLike(
        @RequestBody LikeRequest request,
        Principal principal) {

    if (principal == null) {
        return ResponseEntity.status(HttpStatus.UNAUTHORIZED)
                .body("로그인이 필요합니다.");
    }

    likeLinkService.addLike(
            request.getOriginalLink(),
            principal.getName()
    );

    return ResponseEntity.ok().build();
}

@DeleteMapping("/toggle-like")
public ResponseEntity<?> deleteLike(
        @RequestBody LikeRequest request,
        Principal principal) {

    if (principal == null) {
        return ResponseEntity.status(HttpStatus.UNAUTHORIZED)
                .body("로그인이 필요합니다.");
    }

    likeLinkService.deleteLike(
            request.getOriginalLink(),
            principal.getName()
    );

    return ResponseEntity.ok().build();
}
```

 이건 지금 코드와 거의 동일합니다.

 즉 **Controller 자체가 가장 유력한 문제는 아닙니다.**

 # 10\. 오히려 가장 의심되는 것은 이 3가지입니다

 현재 올려주신 코드만 가지고 우선순위를 정하면:

 ### ① `originalLink`가 실제 DB 값과 다름

 현재:

```
th:data-original-link="${songMainEntity.htmlTitle}"
```

 입니다.

 **`htmlTitle`을 `originalLink`라는 이름의 DB 컬럼에 넣는 게 정말 의도한 것인지 확인하세요.**

---

 ### ② 이미 DB에 좋아요가 있는데 버튼은 `active`가 아님

 현재:

```
const is_liked = like_btn.classList.contains("active");
```

 이기 때문에 DB를 전혀 확인하지 않습니다.

 페이지 최초 진입 시에도 서버에서:

```
boolean isLiked
```

 를 계산해서 Thymeleaf에 전달하는 게 좋습니다.

 예:

```
<button
    type="button"
    class="like_btn"
    th:classappend="${isLiked} ? ' active' : ''"
    th:data-original-link="${songMainEntity.htmlTitle}"
    th:text="${isLiked} ? '좋아요함' : '좋아요'">
    좋아요
</button>
```

---

 ### ③ DELETE 요청이 Spring Security에서 막힘

 POST는 되는데 DELETE만 안 된다면 특히 이 부분을 의심해야 합니다.

 브라우저 Network에서 DELETE 요청의 HTTP status가:

```
403
```

 이라면 Controller까지 도달하지 않은 것입니다.

 현재 JS에서 CSRF를:

```
const csrfToken =
    document.querySelector('meta[name="_csrf"]').content;

const csrfHeader =
    document.querySelector('meta[name="_csrf_header"]').content;
```

 로 가져오는 방식은 일반적으로 맞습니다.

 그래도 `403`이면 Spring Security 설정을 봐야 합니다.

---

 ## 결론

 지금 코드만 보면 **Service와 Controller의 기본적인 POST/DELETE 구조는 크게 잘못되어 있지 않습니다.**

 먼저 브라우저에서 좋아요 버튼을 한 번 누르고 **Network의 상태 코드와 서버 콘솔 로그**를 확인해보세요.

 특히 다음 네 가지 결과만 알면 거의 바로 원인을 특정할 수 있습니다.

```
1. POST 요청 HTTP 상태 코드
2. DELETE 요청 HTTP 상태 코드
3. Controller의 "글 ID / 사용자 ID" 로그가 찍히는지
4. Hibernate에서 INSERT/DELETE SQL이 발생하는지
```

 그리고 **`LikeLinkRepository`와 `LikeLinkEntity` 코드도 보여주시면**, `existsBy...`, `deleteBy...`, `@ManyToOne` 매핑까지 포함해서 **왜 DB에 반영되지 않는지 정확히 짚어드릴 수 있습니다.**
